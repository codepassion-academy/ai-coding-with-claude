## 2. Requirements

### การรับรายงาน

#### RPT-REQ-001 รับรายงานผ่าน API

`POST /reports` รับ JSON ที่มี `districtId`, `landmark`, `depthCm`, `observedAt` เมื่อผ่านการตรวจทุกข้อให้บันทึกและตอบ 201

Acceptance criteria

- AC1: ส่งรายงานที่ถูกต้อง ณ `NOW` ได้ status 201 และ body มี `notice` เท่ากับ `NOTICE`, `label` เท่ากับข้อความป้าย, และ `report` ที่มี `id` (สตริงไม่ว่าง), `districtId: "sai-mai"`, `landmark: "ปากซอยสายไหม 15"`, `depthCm: 25`, `severity: "medium"`, `observedAt: "2026-09-30T19:20:00+07:00"`
- AC2: หลัง AC1 store มีรายงาน 1 รายการ โดย `observedAt` และ `receivedAt` เก็บเป็น UTC (`2026-09-30T12:20:00.000Z` และ `2026-09-30T12:30:00.000Z`)
- AC3: ฟิลด์ที่ไม่รู้จักใน body (เช่น `phone`, `name`) ถูกทิ้ง ไม่อยู่ใน store และไม่อยู่ใน response
- AC4: body ที่ไม่ใช่ JSON object (`undefined`, `null`, array, สตริง, ตัวเลข) ตอบ 400 `{ "error": "invalid report", "fields": ["body"] }`
- AC5: response ของ 201 ไม่มีคีย์ `reporterHash` หรือ IP ในรูปแบบใดๆ

#### RPT-REQ-002 ตรวจเขต

`districtId` ต้องเป็นสตริงที่ตรงกับ id ใน `src/districts.ts` เท่านั้น

Acceptance criteria

- AC1: `districtId: "atlantis"` ตอบ 400 และ `fields` มี `"districtId"`
- AC2: `districtId: "สายไหม"` (ชื่อเขตแทน id) ตอบ 400 และ `fields` มี `"districtId"`
- AC3: ไม่ส่ง `districtId` หรือส่งเป็นตัวเลข ตอบ 400 และ `fields` มี `"districtId"`
- AC4: id ทั้ง 12 ค่าใน `districts` ส่งแล้วได้ 201

#### RPT-REQ-003 ตรวจความลึก

`depthCm` ต้องเป็น JSON number ที่เป็นจำนวนเต็ม 1 ถึง 300 ค่าอื่นปฏิเสธ ไม่ปัดเศษ ไม่แปลงชนิดให้

Acceptance criteria

- AC1: `1` และ `300` ได้ 201
- AC2: `0`, `301`, `-5` ตอบ 400 และ `fields` มี `"depthCm"`
- AC3: `25.5` ตอบ 400 และ `fields` มี `"depthCm"`
- AC4: `"25"` (สตริง), `null`, `true`, และไม่ส่งฟิลด์ ตอบ 400 และ `fields` มี `"depthCm"`

#### RPT-REQ-004 ตรวจเวลาที่เห็น

`observedAt` ต้องเป็นสตริง ISO 8601 ที่ระบุ `Z` หรือ offset (`±hh:mm`) เวลาที่เห็นย้อนหลังได้ไม่เกิน 6 ชั่วโมงจากเวลาเซิร์ฟเวอร์ และล้ำหน้าได้ไม่เกิน 2 นาที เวลาที่ล้ำหน้าภายใน 2 นาทีให้บันทึกเป็นเวลาเซิร์ฟเวอร์

Acceptance criteria (เวลาเซิร์ฟเวอร์ = `NOW`)

- AC1: `2026-09-30T06:30:00Z` (ย้อนหลัง 6 ชั่วโมงพอดี) ได้ 201
- AC2: `2026-09-30T06:29:59Z` ตอบ 400 และ `fields` มี `"observedAt"`
- AC3: `2026-09-30T12:32:00Z` (ล้ำหน้า 2 นาทีพอดี) ได้ 201 และค่าที่เก็บคือ `2026-09-30T12:30:00.000Z`
- AC4: `2026-09-30T12:32:01Z` ตอบ 400 และ `fields` มี `"observedAt"`
- AC5: `2026-09-30T19:20:00+07:00` ได้ 201 และค่าที่เก็บคือ `2026-09-30T12:20:00.000Z`
- AC6: `2026-09-30T12:20:00` (ไม่มี offset), `"เมื่อกี้"`, `1759235400000` (ตัวเลข), `2026-02-30T00:00:00Z` (วันที่ไม่มีจริง) และไม่ส่งฟิลด์ ตอบ 400 และ `fields` มี `"observedAt"`

#### RPT-REQ-005 ตรวจช่องจุดสังเกต

`landmark` ต้องเป็นสตริง ก่อนตรวจให้ normalize เป็น NFC ยุบช่องว่างทุกชนิดที่ติดกัน (รวมขึ้นบรรทัดใหม่และ tab) เป็นช่องว่างเดียว และตัดช่องว่างหัวท้าย ผลที่ได้ต้องยาว 3 ถึง 100 ตัวอักษร (นับเป็น code point) และไม่มีอักขระควบคุม

Acceptance criteria

- AC1: สตริง 3 ตัวอักษร และสตริง 100 ตัวอักษร ได้ 201
- AC2: สตริง 101 ตัวอักษร, `"ab"`, `""`, `"   "` ตอบ 400 และ `fields` มี `"landmark"`
- AC3: `"  ปากซอย \n สายไหม 15  "` ได้ 201 และเก็บเป็น `"ปากซอย สายไหม 15"`
- AC4: สตริงที่มี `\u0000` หรือ `\u001b` ตอบ 400 และ `fields` มี `"landmark"`
- AC5: ไม่ใช่สตริง (ตัวเลข, object, ไม่ส่ง) ตอบ 400 และ `fields` มี `"landmark"`
- AC6: ส่งผิดหลายฟิลด์พร้อมกัน (`districtId: "x"`, `depthCm: 0`) `fields` มีทั้ง `"districtId"` และ `"depthCm"`
- AC7: body ของ 400 ไม่มีค่าที่ผู้ใช้ส่งมา มีเฉพาะชื่อฟิลด์

#### RPT-REQ-006 ปิดเบอร์โทรในช่องจุดสังเกต

ก่อนบันทึก ให้แทนทุกลำดับตัวเลขตั้งแต่ 9 หลักขึ้นไปด้วย `[ปิดเบอร์โทร]` ลำดับตัวเลขหมายถึงตัวเลขอารบิกหรือเลขไทยที่ต่อกัน โดยยอมให้มีตัวคั่น 1 ตัว (ช่องว่าง `-` `.`) ระหว่างหลัก และอาจขึ้นต้นด้วย `+` ข้อความดิบก่อนปิดต้องไม่ถูกเก็บ ไม่ถูกส่งกลับ และไม่ถูกเขียนลง log

Acceptance criteria

- AC1: `"หน้าร้านป้าแดง โทร 081-234-5678"` เก็บและตอบกลับเป็น `"หน้าร้านป้าแดง โทร [ปิดเบอร์โทร]"`
- AC2: `0812345678`, `081 234 5678`, `02-123-4567`, `+66812345678`, `๐๘๑๒๓๔๕๖๗๘` ถูกปิดทุกรูปแบบ
- AC3: `"ซอยลาดพร้าว 101 หน้าเซเว่น"` และ `"สายไหม 15 แยก 3"` ไม่ถูกแก้
- AC4: `"0812345678"` (มีแต่เบอร์โทร) ตอบ 400 และ `fields` มี `"landmark"` เพราะตัดส่วนที่ปิดออกแล้วเหลือข้อความไม่ถึง 3 ตัวอักษร
- AC5: หลังส่ง AC1 เนื้อไฟล์เก็บรายงานและข้อความ log ทั้งหมดไม่มีสตริง `5678`
- AC6: การตรวจความยาว 100 ตัวอักษรของ RPT-REQ-005 ทำกับข้อความก่อนปิดเบอร์โทร

#### RPT-REQ-007 จำกัดจำนวนรายงานต่อ IP

IP หนึ่งส่งรายงานสำเร็จได้ไม่เกิน 5 รายการในช่วง 60 นาทีที่ผ่านมา (นับจาก `receivedAt` ของรายงานใน store) เมื่อโควตาเต็มให้ตอบ 429 ก่อนตรวจเนื้อหา

Acceptance criteria

- AC1: IP เดียวกันส่งรายงานที่ถูกต้อง 5 ครั้ง ณ `NOW` ได้ 201 ทั้งห้า ครั้งที่ 6 ได้ 429 body `{ "error": "rate limit exceeded", "retryAfterSeconds": 3600 }` และ header `Retry-After: 3600`
- AC2: หลัง AC1 store ยังมี 5 รายการ
- AC3: IP อื่น (`203.0.113.11`) ส่ง ณ เวลาเดียวกันได้ 201
- AC4: รายงาน 5 รายการรับเมื่อ 11:30:00Z ส่งครั้งที่ 6 เมื่อ 12:29:59Z ได้ 429 และ `retryAfterSeconds: 1` ส่งเมื่อ 12:30:00Z ได้ 201
- AC5: ส่งรายงานที่ไม่ผ่านการตรวจ 10 ครั้ง (ได้ 400 ทุกครั้ง) แล้วส่งรายงานที่ถูกต้อง ได้ 201 (คำขอที่ถูกปฏิเสธไม่กินโควตา)
- AC6: เมื่อโควตาเต็ม คำขอที่เนื้อหาไม่ถูกต้องก็ได้ 429 ไม่ใช่ 400
- AC7: รายงานที่ถูกซ่อนยังนับในโควตาของผู้ส่ง
- AC8: `ctx.clientIp` ไม่มีค่า ตอบ 500 `{ "error": "client address unavailable" }` และไม่บันทึกรายงาน (จำกัดจำนวนไม่ได้ ต้องไม่รับ)

#### RPT-REQ-008 ตัวตนผู้ส่งเก็บเป็นแฮชเท่านั้น

ระบบเก็บเฉพาะ `HMAC-SHA256(IP_HASH_SECRET, ip)` ในรูป hex ไม่เก็บ IP ดิบ ไม่ส่งแฮชออกทาง API สาธารณะ และล้างแฮชเป็น `null` เมื่อรายงานรับมาครบ 24 ชั่วโมง สำหรับ IPv6 ให้ใช้เฉพาะ 64 บิตแรก และ IPv4 ที่มาในรูป `::ffff:a.b.c.d` ให้ถือเป็น IPv4

Acceptance criteria

- AC1: หลังส่งรายงาน เนื้อไฟล์เก็บรายงานไม่มีสตริง `203.0.113.10` และ `reporterHash` เป็น hex 64 ตัวอักษร
- AC2: IP เดียวกันกับ secret เดียวกันได้แฮชเดียวกัน secret ต่างกันได้แฮชต่างกัน
- AC3: `2001:db8:1:2:aaaa::1` กับ `2001:db8:1:2:bbbb::2` ได้แฮชเดียวกัน ส่วน `2001:db8:1:3::1` ได้แฮชต่าง
- AC4: `::ffff:203.0.113.10` กับ `203.0.113.10` ได้แฮชเดียวกัน
- AC5: `purgeReporterHashes(now)` ทำให้รายงานที่ `receivedAt <= now - 24 ชม.` มี `reporterHash: null` และรายงานที่ใหม่กว่านั้นคงค่าเดิม ฟิลด์อื่นไม่เปลี่ยน
- AC6: body ของ `GET /districts/:id` และ `POST /reports` ไม่มีสตริงแฮชของผู้ส่งรายใด
- AC7: เมื่อ `TRUST_PROXY` ไม่ได้ตั้ง ค่า header `X-Forwarded-For` ไม่มีผลต่อ `clientIp`

### การแสดงผล

#### RPT-REQ-009 แสดงรายงานแยกจากค่าสถานี พร้อมป้าย

`GET /districts/:id` เพิ่มคีย์ `reports` ที่มี `label` และ `items` คีย์ `notice`, `district`, `stations` คงรูปและค่าเดิม ค่าจากรายงานไม่ปรากฏใน `stations` และไม่มีผลต่อ `latest` ของสถานี

Acceptance criteria

- AC1: `GET /districts/lat-phrao` เมื่อ store ว่าง ได้ `reports: { label: <ข้อความป้าย>, items: [] }` และ `stations` เท่ากับผลก่อนมีฟีเจอร์นี้ทุกประการ
- AC2: หลังส่งรายงานที่ถูกต้อง `GET /districts/sai-mai` ณ `NOW` ได้ `stations: []` และ `reports.items` มี 1 รายการ `{ landmark: "ปากซอยสายไหม 15", depthCm: 25, severity: "medium", observedAt: "2026-09-30T19:20:00+07:00", minutesAgo: 10, reporterCount: 1 }`
- AC3: รายงานของ `sai-mai` ไม่ปรากฏใน `GET /districts/lat-phrao`
- AC4: ส่งรายงานเขต `lat-phrao` ความลึก 250 แล้ว `stations[0].latest.levelCm` ยังเป็น 104
- AC5: `reports.label` มีทั้งข้อความ "รายงานจากประชาชน" และ "ไม่ใช่ประกาศเตือนภัยทางการ" และมีอยู่เสมอแม้ `items` ว่าง
- AC6: `items` เรียงจากเวลาที่เห็นล่าสุดไปเก่าสุด
- AC7: รายการใน `items` มีเฉพาะคีย์ `landmark`, `depthCm`, `severity`, `observedAt`, `minutesAgo`, `reporterCount`

#### RPT-REQ-010 อายุรายงานและ "เมื่อ X นาทีที่แล้ว"

รายงานที่ใช้แสดงผลคือรายงานที่ไม่ถูกซ่อนและ `now - observedAt < 6 ชั่วโมง` รายงานที่พ้นอายุไม่แสดงแต่ยังอยู่ใน store `minutesAgo` คือจำนวนนาทีเต็ม (ปัดลง) จากเวลาที่เห็นล่าสุดของรายการถึง `now`

Acceptance criteria

- AC1: รายงานเห็นเมื่อ 12:20:00Z ดู ณ 18:19:59Z ยังแสดง และ `minutesAgo: 359`
- AC2: ดู ณ 18:20:00Z (ครบ 6 ชั่วโมงพอดี) ไม่แสดง และ store ยังมีรายงานนั้น
- AC3: รายงานเห็นเมื่อ 12:20:00Z ดู ณ 12:20:59Z ได้ `minutesAgo: 0` ดู ณ 12:21:00Z ได้ `minutesAgo: 1`
- AC4: `minutesAgo` เป็นจำนวนเต็มไม่ติดลบเสมอ

#### RPT-REQ-011 รวมรายงานซ้ำ

รายงานที่ใช้แสดงผล (ตาม RPT-REQ-010) ซึ่งมีเขตเดียวกันและ `landmarkKey` เดียวกัน ให้เรียงตามเวลาที่เห็น แล้วรวมรายงานที่อยู่ติดกันและห่างกันไม่เกิน 30 นาทีเป็นรายการเดียว ช่องว่างที่เกิน 30 นาทีเริ่มรายการใหม่ แต่ละรายการแสดงข้อมูลของรายงานที่เห็นล่าสุดในกลุ่ม (ถ้าเวลาที่เห็นเท่ากันใช้รายงานที่ `receivedAt` หลังสุด) และ `reporterCount` คือจำนวน `reporterHash` ที่ไม่ซ้ำในกลุ่ม

`landmarkKey` ได้จากข้อความที่ปิดเบอร์โทรแล้ว โดย normalize NFC, แปลงเลขไทยเป็นอารบิก, ทำเป็นตัวพิมพ์เล็ก, ลบช่องว่างทั้งหมด, แล้วตัดคำนำหน้าตามตาราง 1.2 จากต้นข้อความซ้ำจนไม่เหลือ (ถ้าตัดแล้วเหลือข้อความว่างให้ใช้ข้อความก่อนตัด)

Acceptance criteria

- AC1: IP A รายงาน `"ปากซอยสายไหม 15"` ลึก 20 เห็นเมื่อ 12:00Z และ IP B รายงาน `"ปากซอย สายไหม15"` ลึก 35 เห็นเมื่อ 12:25Z ดู ณ `NOW` ได้ 1 รายการ `depthCm: 35`, `severity: "high"`, `observedAt` เป็น 19:25 เวลากรุงเทพฯ, `reporterCount: 2`, `landmark: "ปากซอย สายไหม15"`
- AC2: รายงานที่สองเห็นเมื่อ 12:30:00Z (ห่าง 30 นาทีพอดี) ยังรวมเป็น 1 รายการ เห็นเมื่อ 12:30:01Z จากรายงานแรก 12:00:00Z ได้ 2 รายการ
- AC3: รายงานสามรายการเห็นเมื่อ 11:30Z, 11:55Z, 12:20Z รวมเป็น 1 รายการ (หน้าต่างเลื่อนตามรายงานล่าสุด แม้รายการแรกกับรายการสุดท้ายห่างกัน 50 นาที)
- AC4: IP เดียวกันรายงานจุดเดียวกัน 3 ครั้งภายใน 30 นาที ได้ 1 รายการ `reporterCount: 1`
- AC5: `"หน้า Big C สายไหม"`, `"บริเวณหน้า big c สายไหม"`, `"BIG C สายไหม"` มี `landmarkKey` เดียวกัน
- AC6: `"ตรงข้ามเซเว่น"` กับ `"เซเว่น"` มี `landmarkKey` ต่างกัน ส่วน `"ตรงเซเว่น"` กับ `"เซเว่น"` เท่ากัน
- AC7: จุดสังเกตเดียวกันแต่คนละเขตไม่รวมกัน
- AC8: `"บริเวณ"` มี `landmarkKey` เป็น `"บริเวณ"` และ `"บริเวณหน้า"` มี `landmarkKey` เป็น `"หน้า"` (ไม่ตัดจนว่าง)
- AC9: รายงานเห็นเมื่อ 12:00Z ลึก 40 รับเมื่อ 12:10Z และรายงานเห็นเมื่อ 12:00Z ลึก 10 รับเมื่อ 12:05Z รายการที่แสดงมี `depthCm: 40`
- AC10: การรวมไม่แก้ข้อมูลใน store จำนวนรายงานใน store เท่ากับจำนวนที่รับสำเร็จ

#### RPT-REQ-012 ระดับความรุนแรง (เกณฑ์ชั่วคราว)

`severity` คำนวณจาก `depthCm` เท่านั้น: 1 ถึง 15 เป็น `"low"`, 16 ถึง 30 เป็น `"medium"`, 31 ถึง 300 เป็น `"high"` เกณฑ์อยู่ในค่าคงที่ชุดเดียว และไม่เก็บ `severity` ลง store (คำนวณตอนตอบ) เพื่อให้เปลี่ยนเกณฑ์ได้โดยไม่ต้องแก้ข้อมูลเก่า

Acceptance criteria

- AC1: `severityOf(1)` และ `severityOf(15)` ได้ `"low"`
- AC2: `severityOf(16)` และ `severityOf(30)` ได้ `"medium"`
- AC3: `severityOf(31)` และ `severityOf(300)` ได้ `"high"`
- AC4: รายงานใน store ไม่มีคีย์ `severity`
- AC5: หน้าเว็บแสดงระดับเป็นคำว่า ต่ำ กลาง สูง คู่กับตัวเลขเซนติเมตรเสมอ ไม่แสดงระดับอย่างเดียว

### ผู้ดูแลระบบ

#### RPT-REQ-013 ซ่อนและยกเลิกการซ่อนรายงาน

ผู้ดูแลระบบซ่อนรายงานรายตัวได้ด้วย `POST /admin/reports/:id/hide` และยกเลิกด้วย `POST /admin/reports/:id/unhide` การซ่อนตั้ง `hiddenAt` ไม่ลบข้อมูล รายงานที่ถูกซ่อนไม่ถูกนำไปแสดง ไม่ถูกนับใน `reporterCount` และไม่ถูกใช้เป็นความลึกล่าสุด `GET /admin/reports` แสดงรายงานที่รับใน 24 ชั่วโมงล่าสุดทั้งที่ซ่อนและไม่ซ่อน

Acceptance criteria

- AC1: ซ่อนรายงานเดียวของ `sai-mai` แล้ว `GET /districts/sai-mai` ได้ `reports.items: []` และ store ยังมีรายงานนั้นพร้อม `hiddenAt` เป็นเวลา UTC
- AC2: กลุ่มที่มีรายงานลึก 20 (12:00Z, IP A) และ 35 (12:25Z, IP B) ซ่อนรายการหลังแล้ว รายการที่แสดงมี `depthCm: 20`, `reporterCount: 1`
- AC3: ยกเลิกการซ่อนแล้วรายงานกลับมาแสดง และ `hiddenAt` เป็น `null`
- AC4: ซ่อนซ้ำหรือยกเลิกซ้ำได้ 200 และสถานะไม่เปลี่ยน (`hiddenAt` ของการซ่อนครั้งแรกคงเดิม)
- AC5: id ที่ไม่มีอยู่ตอบ 404 `{ "error": "unknown report" }`
- AC6: `GET /admin/reports` ณ `NOW` แสดงรายงานที่รับเมื่อ 09-29T12:30:01Z แต่ไม่แสดงที่รับเมื่อ 09-29T12:30:00Z เรียงจาก `receivedAt` ใหม่ไปเก่า
- AC7: แต่ละรายการของ `GET /admin/reports` มีคีย์ `id`, `districtId`, `landmark`, `depthCm`, `observedAt`, `receivedAt`, `hiddenAt`, `reporterRef` โดย `reporterRef` คือ 8 ตัวอักษรแรกของแฮช (หรือ `null`) ไม่มีแฮชเต็มและไม่มี IP
- AC8: ไม่มี route ใดลบรายงานออกจาก store (`DELETE` ทุก path ตอบ 404)

#### RPT-REQ-014 ช่องทางผู้ดูแลระบบป้องกันด้วยรหัสลับ

ทุก route ใต้ `/admin/` ต้องมี header `Authorization: Bearer <token>` ที่ตรงกับ env `ADMIN_TOKEN` เปรียบเทียบแบบใช้เวลาคงที่ รหัสไม่อยู่ในโค้ด ไม่อยู่ใน repo และไม่ถูกเขียนลง log ถ้าไม่ได้ตั้ง `ADMIN_TOKEN` หรือสั้นกว่า 16 ตัวอักษร ช่องทางผู้ดูแลถูกปิด การยืนยันตัวผิดถูกจำกัด 10 ครั้งต่อ 15 นาทีต่อ IP

Acceptance criteria

- AC1: ไม่มี header `Authorization` ตอบ 401 พร้อม header `WWW-Authenticate: Bearer` และรายงานไม่ถูกซ่อน
- AC2: token ผิด, token ถูกแต่ไม่มีคำว่า `Bearer`, และ token ที่เป็น prefix ของค่าจริง ตอบ 401
- AC3: token ถูกต้อง ตอบ 200
- AC4: `adminToken` ไม่ได้ตั้ง หรือยาว 15 ตัวอักษร ทุก route ใต้ `/admin/` ตอบ 503 `{ "error": "admin disabled" }` แม้ส่ง token ที่ตรงกัน
- AC5: IP เดียวกันยืนยันตัวผิด 10 ครั้งใน 15 นาที ครั้งที่ 11 ตอบ 429 แม้ token ถูก IP อื่นไม่ได้รับผล
- AC6: ค้นใน `src/`, `public/`, `tests/`, `README.md` ไม่พบค่า token จริง test ใช้ token ที่สร้างในตัว test เอง
- AC7: ข้อความ log ของคำขอที่ยืนยันตัวผิดไม่มีค่า token ที่ส่งมา
- AC8: response ของ 401 และ 404 ใต้ `/admin/` ไม่บอกว่ารายงาน id นั้นมีอยู่หรือไม่ก่อนยืนยันตัวผ่าน (ตรวจ token ก่อนค้นรายงาน)

### การเก็บข้อมูล

#### RPT-REQ-015 เก็บรายงานลงไฟล์หลังอินเทอร์เฟซเดียว

โค้ดส่วนอื่นเข้าถึงรายงานผ่านอินเทอร์เฟซ `ReportStore` เท่านั้น มี implementation 2 แบบ: ในหน่วยความจำ (สำหรับ test) และไฟล์ JSON ไฟล์เขียนแบบ atomic (เขียนไฟล์ชั่วคราวแล้ว rename) รายงานไม่ถูกลบ

Acceptance criteria

- AC1: ชุด test เดียวกัน (contract test) ผ่านทั้ง memory store และ file store
- AC2: เพิ่มรายงานด้วย file store แล้วสร้าง file store ใหม่จาก path เดิม อ่านได้รายงานเดิมครบทุกฟิลด์
- AC3: path ที่ยังไม่มีไฟล์ เริ่มด้วย store ว่าง และสร้างโฟลเดอร์ให้เมื่อเขียนครั้งแรก
- AC4: ไฟล์ที่เนื้อหาไม่ใช่ JSON หรือรูปแบบไม่ตรง ทำให้การสร้าง store โยน error ที่ระบุ path และไฟล์เดิมไม่ถูกแก้
- AC5: เมื่อการเขียนไฟล์ล้มเหลว `add` โยน error, `POST /reports` ตอบ 500 `{ "error": "could not save report" }` และ `all()` ไม่มีรายงานนั้น
- AC6: `src/app.ts` ไม่ import `node:fs`
- AC7: `var/` อยู่ใน `.gitignore`

### หน้าเว็บ

#### RPT-REQ-016 หน้าเว็บฟอร์มรายงาน

`GET /report` ตอบหน้า HTML ภาษาไทยที่มีฟอร์ม 4 ช่อง (เขตเป็นรายการให้เลือก, จุดสังเกต, ความลึก, เวลาที่เห็น) ส่งข้อมูลไปที่ `POST /reports` และแสดงรายงานจากประชาชนของเขตที่เลือกพร้อมป้าย หน้าเว็บไม่ขอชื่อหรือเบอร์โทร

Acceptance criteria

- AC1: `GET /report` ตอบ 200 `content-type: text/html; charset=utf-8` และ `GET /report.js` ตอบ 200 `content-type: text/javascript; charset=utf-8`
- AC2: HTML มี `NOTICE` และข้อความป้าย และมีข้อความบอกว่าอย่าใส่ชื่อหรือเบอร์โทรในช่องจุดสังเกต
- AC3: HTML มี `<select name="districtId">`, `<input name="landmark" maxlength="100">`, `<input name="depthCm" type="number" min="1" max="300" step="1">`, `<input name="observedAt" type="datetime-local">` ไม่มีช่องกรอกชื่อเขตเป็นข้อความ และไม่มีช่องชื่อหรือเบอร์โทร
- AC4: response ของ `GET /report` มี header `Content-Security-Policy: default-src 'self'` และ `X-Content-Type-Options: nosniff` และ HTML ไม่มี inline script
- AC5: `public/report.js` ไม่ใช้ `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` (ข้อความจากผู้ใช้แสดงด้วย `textContent`)
- AC6: `public/report.js` เรียกเฉพาะ path ภายในแอป (`/districts`, `/districts/:id`, `/reports`) ไม่มี URL ภายนอก
- AC7 (ตรวจด้วยมือ): ที่ความกว้าง 360px ใช้งานฟอร์มได้โดยไม่ต้องเลื่อนแนวนอน รายการเขตมี 12 เขต เวลาที่เห็นตั้งต้นเป็นเวลาปัจจุบันของเครื่อง ส่งสำเร็จแล้วรายงานขึ้นในรายการพร้อม "เมื่อ X นาทีที่แล้ว" ส่งไม่ผ่านแสดงข้อความภาษาไทยตามฟิลด์ที่ผิด ได้ 429 แสดงข้อความว่าส่งบ่อยเกินไป

### ข้อกำหนดร่วม

#### RPT-REQ-017 log ไม่มีข้อมูลส่วนบุคคล

log ของฟีเจอร์นี้เขียนผ่าน logger ที่ฉีดเข้ามา แต่ละบรรทัดมีเฉพาะชื่อเหตุการณ์, `id` ของรายงาน, `districtId`, status และชื่อฟิลด์ที่ไม่ผ่าน ห้ามมีข้อความจุดสังเกต (ทั้งก่อนและหลังปิดเบอร์โทร), body ดิบ, IP, แฮชผู้ส่ง และ token เหตุการณ์ที่ต้องมี: `report.accepted`, `report.rejected` (พร้อม `reason: "validation" | "rate_limit"`), `report.hidden`, `report.unhidden`, `admin.auth_failed`

Acceptance criteria

- AC1: ส่งรายงานที่มี `landmark: "บ้านคุณสมชาย 0812345678"` จาก `203.0.113.10` แล้ว log ที่เก็บได้ไม่มี `สมชาย`, `0812345678`, `203.0.113.10`
- AC2: รายงานที่รับสำเร็จมี log `report.accepted` 1 บรรทัดที่มี `id` ตรงกับ response
- AC3: รายงานที่ไม่ผ่านการตรวจมี log `report.rejected` ที่มี `reason: "validation"` และชื่อฟิลด์ ไม่มีค่าที่ส่งมา
- AC4: คำขอที่ได้ 429 มี log `report.rejected` ที่มี `reason: "rate_limit"`
- AC5: `src/server.ts` ไม่ log body ของคำขอและไม่ log header `Authorization`

#### RPT-REQ-018 ของเดิมไม่พัง

route เดิมให้ผลเดิม test เดิมผ่านโดยไม่แก้ `NOTICE` คงข้อความเดิมและอยู่ในทุก response ที่เป็น JSON 2xx ของ route สาธารณะ

Acceptance criteria

- AC1: `tests/app.test.ts` และ `tests/time.test.ts` ฉบับปัจจุบันผ่านโดยไม่แก้แม้แต่บรรทัดเดียว
- AC2: `handle("GET", "/districts", undefined, { now })` ยังเรียกได้ด้วย context ที่มีแค่ `now`
- AC3: body ของ `GET /districts` เท่ากับผลก่อนมีฟีเจอร์นี้ทุกประการ
- AC4: ค่าของ `NOTICE` ไม่เปลี่ยน
- AC5: `npm test` และ `npm run lint` ผ่าน

#### RPT-REQ-019 จำกัดขนาดและรูปแบบคำขอ

`src/server.ts` รับ body ได้ไม่เกิน 10 KB เกินให้ตอบ 413 และหยุดอ่าน JSON ที่ parse ไม่ได้ตอบ 400 เหมือนเดิม

Acceptance criteria

- AC1: body ขนาด 10,241 ไบต์ ตอบ 413 `{ "error": "payload too large" }`
- AC2: body `{bad` ตอบ 400 `{ "error": "invalid JSON" }`
- AC3: `GET /reports`, `PUT /reports`, `DELETE /reports` ตอบ 404

#### RPT-REQ-020 ไม่ติดต่อระบบจริง

โค้ดและ test ของฟีเจอร์นี้ไม่ส่งคำขอออกนอกเครื่อง โดยเฉพาะไม่ส่งไปที่ `flood-api.rooptanjai.com`

Acceptance criteria

- AC1: ค้นใน `src/`, `public/`, `tests/` ไม่พบ `rooptanjai`
- AC2: `src/` ไม่เรียก `fetch`, `http.request`, `https.request`
- AC3: test ทั้งหมดเรียก `handle` ตรงๆ หรือใช้ store ในหน่วยความจำหรือโฟลเดอร์ชั่วคราว ไม่เปิด socket ออกนอกเครื่อง

## 3. Design

### 3.1 Data model

รายงานที่เก็บ (หนึ่งรายการต่อการส่งสำเร็จหนึ่งครั้ง ไม่เก็บผลการรวม)

```ts
type Report = {
  id: string                  // crypto.randomUUID()
  districtId: string          // id จาก src/districts.ts
  landmark: string            // ปิดเบอร์โทรและยุบช่องว่างแล้ว ใช้แสดงผล
  landmarkKey: string         // ข้อความที่ปรับรูปแล้ว ใช้จับคู่
  depthCm: number             // จำนวนเต็ม 1..300
  observedAt: string          // UTC ISO เช่น "2026-09-30T12:20:00.000Z"
  receivedAt: string          // UTC ISO เวลาเซิร์ฟเวอร์ตอนรับ
  reporterHash: string | null // HMAC-SHA256 hex, null หลัง 24 ชม.
  hiddenAt: string | null     // UTC ISO ตอนถูกซ่อน
}
```

รายการที่แสดงต่อสาธารณะ (คำนวณทุกครั้งที่ตอบ ไม่เก็บ)

```ts
type ReportItem = {
  landmark: string
  depthCm: number
  severity: "low" | "medium" | "high"
  observedAt: string   // เวลากรุงเทพฯ จาก toBangkokIso
  minutesAgo: number
  reporterCount: number
}
```

ส่วนเก็บข้อมูล

```ts
interface ReportStore {
  all(): readonly Report[]
  add(report: Report): void                 // โยน error ถ้าเขียนไม่สำเร็จ
  setHidden(id: string, hiddenAt: string | null): Report | undefined
  purgeReporterHashes(now: Date): number    // คืนจำนวนที่ล้าง
}
```

- ทุก method เป็น synchronous เพื่อให้ `handle` ยังเป็น synchronous เหมือนเดิม และการตรวจโควตากับการบันทึกเกิดต่อเนื่องกันโดยไม่มีคำขออื่นแทรก
- file store โหลดไฟล์ครั้งเดียวตอนสร้าง เก็บสำเนาในหน่วยความจำ ทุกการเปลี่ยนแปลงเขียนทั้งไฟล์ลง `<path>.tmp` แล้ว `renameSync` ทับ ถ้าเขียนไม่สำเร็จให้ย้อนสำเนาในหน่วยความจำ
- รูปแบบไฟล์: `{ "version": 1, "reports": Report[] }`
- ข้อจำกัดที่ยอมรับ: เซิร์ฟเวอร์เครื่องเดียว process เดียว และเขียนทั้งไฟล์ทุกครั้ง (ช้าลงตามจำนวนรายงานสะสม)

### 3.2 API

| Method และ path | สถานะ | ใครเรียก |
| --------------- | ----- | -------- |
| `GET /districts` | ไม่เปลี่ยน | สาธารณะ |
| `GET /districts/:id` | เพิ่มคีย์ `reports` | สาธารณะ |
| `POST /reports` | ใหม่ | สาธารณะ จำกัดจำนวนต่อ IP |
| `GET /report`, `GET /report.js` | ใหม่ | สาธารณะ |
| `GET /admin/reports` | ใหม่ | ผู้ดูแลระบบ |
| `POST /admin/reports/:id/hide` | ใหม่ | ผู้ดูแลระบบ |
| `POST /admin/reports/:id/unhide` | ใหม่ | ผู้ดูแลระบบ |

`POST /reports`

```jsonc
// คำขอ
{ "districtId": "sai-mai", "landmark": "ปากซอยสายไหม 15", "depthCm": 25, "observedAt": "2026-09-30T19:20:00+07:00" }

// 201
{
  "notice": "<NOTICE>",
  "label": "รายงานจากประชาชน ยังไม่ยืนยัน ไม่ใช่ประกาศเตือนภัยทางการ",
  "report": {
    "id": "0b6f…", "districtId": "sai-mai", "landmark": "ปากซอยสายไหม 15",
    "depthCm": 25, "severity": "medium", "observedAt": "2026-09-30T19:20:00+07:00"
  }
}

// 400
{ "error": "invalid report", "fields": ["depthCm", "observedAt"] }

// 429 พร้อม header Retry-After
{ "error": "rate limit exceeded", "retryAfterSeconds": 1200 }
```

ลำดับการทำงานของ `POST /reports`

1. ไม่มี `clientIp` ตอบ 500
2. คำนวณแฮชผู้ส่ง นับรายงานของแฮชนั้นที่ `receivedAt > now - 60 นาที` ถ้าครบ 5 ตอบ 429 โดย `retryAfterSeconds` คือเวลาที่รายงานเก่าสุดในหน้าต่างจะพ้น 60 นาที (ปัดขึ้นเป็นวินาที)
3. ตรวจทุกฟิลด์ รวบรวมชื่อฟิลด์ที่ผิดทั้งหมด ถ้ามีตอบ 400
4. ปิดเบอร์โทร สร้าง `landmarkKey` ปรับเวลาที่ล้ำหน้าเป็นเวลาเซิร์ฟเวอร์
5. `store.add` ถ้าล้มเหลวตอบ 500
6. ตอบ 201

`GET /districts/:id` (ส่วนที่เพิ่ม)

```jsonc
{
  "notice": "<NOTICE>",
  "district": { "id": "sai-mai", "nameTh": "สายไหม", "nameEn": "Sai Mai" },
  "stations": [],
  "reports": {
    "label": "รายงานจากประชาชน ยังไม่ยืนยัน ไม่ใช่ประกาศเตือนภัยทางการ",
    "items": [
      { "landmark": "ปากซอยสายไหม 15", "depthCm": 25, "severity": "medium",
        "observedAt": "2026-09-30T19:20:00+07:00", "minutesAgo": 10, "reporterCount": 1 }
    ]
  }
}
```

ขั้นตอนสร้าง `items`: กรองรายงานของเขตที่ `hiddenAt` เป็น `null` และ `now - observedAt < 6 ชม.` จัดกลุ่มตาม `landmarkKey` เรียงตาม `observedAt` แล้ว `receivedAt` ตัดกลุ่มเมื่อช่องว่างเกิน 30 นาที สร้างรายการจากรายงานสุดท้ายของแต่ละกลุ่ม แล้วเรียงรายการจากใหม่ไปเก่า

Route ผู้ดูแลระบบ

```jsonc
// GET /admin/reports  → 200
{ "reports": [ { "id": "0b6f…", "districtId": "sai-mai", "landmark": "ปากซอยสายไหม 15", "depthCm": 25,
                 "observedAt": "2026-09-30T19:20:00+07:00", "receivedAt": "2026-09-30T19:30:00+07:00",
                 "hiddenAt": null, "reporterRef": "a1b2c3d4" } ] }

// POST /admin/reports/:id/hide และ /unhide → 200
{ "report": { /* รูปเดียวกับด้านบน */ } }
```

ลำดับการตรวจของ route ผู้ดูแล: ช่องทางถูกปิดตอบ 503, IP ถูกจำกัดตอบ 429, token ไม่ผ่านตอบ 401 (และนับความผิดพลาด), จากนั้นจึงค้นรายงาน ตัวนับการยืนยันตัวผิดเก็บในหน่วยความจำ (หายเมื่อ restart)

การเปลี่ยนแปลงของ type ใน `src/app.ts`

```ts
export type Response = { status: number; body: unknown; headers?: Record<string, string> }
export type Context = { now: Date; clientIp?: string; authorization?: string }

export type AppDeps = {
  store: ReportStore
  ipHashSecret: string
  adminToken?: string
  log: (event: string, fields: Record<string, unknown>) => void
  assets: { reportHtml: string; reportJs: string }
}
export function createApp(deps: AppDeps): typeof handle
export function handle(method: string, path: string, body: unknown, ctx?: Context): Response
```

- `handle` ที่ export อยู่เดิมยังอยู่ และผูกกับ memory store ว่าง, secret สุ่มต่อ process, ไม่มี `adminToken`, logger ที่ไม่ทำอะไร test เดิมจึงไม่ต้องแก้
- test ใหม่ใช้ `createApp` กับ memory store ของตัวเองเพื่อไม่ให้ข้อมูลรั่วข้าม test
- เมื่อ `headers` มี `content-type` และ `body` เป็นสตริง `server.ts` ส่ง body ตามนั้นโดยไม่ `JSON.stringify`

Environment variables (อ่านใน `src/server.ts` เท่านั้น)

| ตัวแปร | ความหมาย | ถ้าไม่ตั้ง |
| ------ | -------- | ---------- |
| `REPORTS_FILE` | path ของไฟล์เก็บรายงาน | `var/reports.json` |
| `IP_HASH_SECRET` | กุญแจของ HMAC | สุ่มใหม่ทุกครั้งที่เริ่ม process และเตือนใน log ว่าโควตาจะรีเซ็ตเมื่อ restart |
| `ADMIN_TOKEN` | รหัสลับผู้ดูแลระบบ อย่างน้อย 16 ตัวอักษร | ช่องทางผู้ดูแลถูกปิด (503) |
| `TRUST_PROXY` | `1` เมื่ออยู่หลัง reverse proxy ชั้นเดียว ใช้ค่าสุดท้ายใน `X-Forwarded-For` | ใช้ที่อยู่ของ socket |

## 4. Edge cases

1. **เวลาที่เห็นย้อนหลัง 6 ชั่วโมงพอดี** รับได้ (RPT-REQ-004 AC1) แต่ไม่แสดงเลย เพราะการแสดงต้องอายุน้อยกว่า 6 ชั่วโมง (RPT-REQ-010 AC2) รายงานยังถูกเก็บและกินโควตา
2. **นาฬิกาเครื่องผู้ใช้เดินเร็ว** ล้ำหน้าไม่เกิน 2 นาทีถูกบันทึกเป็นเวลาเซิร์ฟเวอร์ `minutesAgo` จึงไม่ติดลบ เกิน 2 นาทีปฏิเสธ
3. **จุดสังเกตมีแต่เบอร์โทร** ปิดแล้วไม่เหลือข้อความ ตอบ 400 (RPT-REQ-006 AC4)
4. **เบอร์โทรเขียนหลายแบบ** มีขีด มีช่องว่าง ขึ้นต้น +66 หรือเป็นเลขไทย ถูกปิดทั้งหมด เลขซอยและเลขแยก (น้อยกว่า 9 หลัก) ไม่โดน เบอร์ที่เขียนเป็นตัวหนังสือ ("ศูนย์แปดหนึ่ง…") หรือคั่นด้วยคำอื่นหลุดได้ ยอมรับในรอบนี้และให้ผู้ดูแลซ่อน
5. **เลขยาวที่ไม่ใช่เบอร์โทร** เช่น เลขบัตรประชาชน 13 หลัก ถูกปิดด้วยกฎเดียวกัน ถือว่าถูกต้องเพราะเป็นข้อมูลส่วนบุคคลเหมือนกัน
6. **คนเดียวส่งจุดเดิมหลายครั้ง** รวมเป็นรายการเดียว `reporterCount` เป็น 1 และความลึกเป็นค่าล่าสุดของเขา
7. **หลายคนใช้ IP เดียวกัน** (Wi-Fi ร้าน, NAT ของเครือข่ายมือถือ) ใช้โควตา 5 รายการร่วมกัน และนับเป็นผู้รายงาน 1 คน ยอมรับในรอบนี้
8. **รายงานมาช้าเชื่อมสองกลุ่ม** กลุ่ม 11:30Z กับ 12:20Z แยกกัน เมื่อมีรายงานเห็นเมื่อ 11:55Z เข้ามาทีหลัง สามรายการรวมเป็นรายการเดียว เพราะการรวมคำนวณใหม่ทุกครั้งจากเวลาที่เห็น
9. **ซ่อนรายงานตัวกลางของกลุ่ม** ถ้าช่องว่างที่เหลือเกิน 30 นาที กลุ่มแตกเป็นสองรายการ ยกเลิกการซ่อนแล้วกลับมารวม
10. **ซ่อนรายงานล่าสุดของกลุ่ม** รายการแสดงความลึกและเวลาของรายงานก่อนหน้าแทน ซ่อนครบทุกรายงานรายการหายไป
11. **ยกเลิกการซ่อนหลังรายงานพ้น 6 ชั่วโมง** สำเร็จ (200) แต่ไม่กลับมาแสดง
12. **เวลาที่เห็นเท่ากันทุกประการ** ใช้รายงานที่เซิร์ฟเวอร์รับทีหลังเป็นค่าล่าสุด (RPT-REQ-011 AC9)
13. **จุดสังเกตเดียวกันแต่เขียนต่างกัน** เช่น "เซเว่น" กับ "7-11" หรือสะกดผิด ไม่รวมกัน แสดงเป็นสองรายการ intent ยอมรับข้อนี้แล้ว
14. **เขตที่ไม่มีสถานีวัด** (`sai-mai`) ได้ `stations: []` คู่กับ `reports.items` ที่มีข้อมูล เป็นกรณีหลักที่ฟีเจอร์นี้ต้องรองรับ
15. **`depthCm` เป็น `25.0`** JSON แยกจาก `25` ไม่ได้ จึงรับ ส่วน `25.5`, `"25"`, `2.5e1` ที่เป็นสตริงปฏิเสธ
16. **ข้อความจุดสังเกตเป็น HTML หรือ script** เก็บเป็นข้อความธรรมดา API ตอบเป็น JSON และหน้าเว็บแสดงด้วย `textContent` พร้อม CSP จึงไม่ถูกรันเป็นโค้ด
17. **ปลอม header `X-Forwarded-For`** ไม่มีผลเมื่อไม่ได้ตั้ง `TRUST_PROXY` ถ้าตั้งไว้แต่ไม่มี proxy จริง ผู้ส่งเลี่ยงโควตาได้ จึงต้องตั้งเฉพาะเมื่ออยู่หลัง proxy
18. **ผู้ส่งใช้ IPv6** นับโควตาต่อ /64 เพื่อไม่ให้หมุนที่อยู่ในเครือข่ายเดียวกันแล้วเลี่ยงโควตา
19. **เซิร์ฟเวอร์ restart** โควตาต่อ IP ยังอยู่เพราะนับจากไฟล์ (ถ้าตั้ง `IP_HASH_SECRET`) ส่วนตัวนับการยืนยันตัวผู้ดูแลผิดรีเซ็ต
20. **ไฟล์เก็บรายงานเสีย** เซิร์ฟเวอร์ไม่เริ่มทำงานและไม่เขียนทับไฟล์ ให้คนตรวจก่อน
21. **ดิสก์เต็มหรือเขียนไฟล์ไม่ได้** ตอบ 500 รายงานไม่ค้างในหน่วยความจำ ผู้ใช้ส่งใหม่ได้โดยไม่เสียโควตา
22. **โควตาเต็มตรงขอบเวลา** รายงานที่รับครบ 60 นาทีพอดีไม่ถูกนับแล้ว (RPT-REQ-007 AC4)
23. **ล้างแฮชหลัง 24 ชั่วโมง** ไม่กระทบ `reporterCount` เพราะรายงานที่ยังแสดงอยู่รับมาไม่เกิน 6 ชั่วโมงเสมอ

รอบนี้ไม่ทำ

- ให้เจ้าของรายงานแก้หรือลบรายงานของตัวเอง และระบบล็อกอินของผู้รายงาน
- ฐานข้อมูล การรันหลายเครื่องหรือหลาย process และการหมุนหรือบีบอัดไฟล์เก็บรายงาน
- ช่องทางอื่นนอกจาก API และหน้าเว็บ เช่น LINE
- รูปภาพ พิกัด GPS แผนที่ และการเลือกจุดสังเกตจากรายการ
- การยืนยันรายงานโดยเจ้าหน้าที่ และการนำรายงานไปรวมหรือปรับค่าของสถานีวัด
- เกณฑ์ระดับความรุนแรงฉบับจริง (รอบนี้ใช้เกณฑ์ชั่วคราว)
- หน้าจอสำหรับผู้ดูแลระบบ (ใช้ `curl` กับ API), บัญชีผู้ดูแลหลายคน, การบันทึกเหตุผลที่ซ่อน และขั้นตอนอุทธรณ์
- CAPTCHA, การตรวจสแปมอัตโนมัติ, การบล็อก IP และการจำกัดจำนวนคำขอ GET
- ประกาศความเป็นส่วนตัวและการขอความยินยอมตาม PDPA (รอฝ่ายกฎหมาย)
- หลายภาษา และการรับรองมาตรฐานการเข้าถึง
- แดชบอร์ดตัวชี้วัด (รอบนี้มีแค่ log เหตุการณ์ตาม RPT-REQ-017 ให้นับภายหลังได้)
- เขตที่เหลืออีก 38 เขต และจำนวนรายงานต่อเขตใน `GET /districts`
- หน้าเว็บแสดงค่าสถานีวัด (หน้า `/report` แสดงเฉพาะฟอร์มและรายงานจากประชาชน)
- การแจ้งเตือนผู้ใช้
- การส่งหรือดึงข้อมูลจากระบบจริง (`flood-api.rooptanjai.com`)

## 6. คำถามที่ยังเปิดอยู่

ไม่มีข้อใดกั้นการเริ่มทำ ค่าที่เกี่ยวข้องอยู่ในค่าคงที่และแก้ได้ที่จุดเดียว

| # | เรื่อง | ค่าที่ใช้ไปก่อน | ใครต้องตอบ |
| - | ------ | --------------- | ---------- |
| 1 | อายุรายงาน 6 ชั่วโมง และหน้าต่างรวม 30 นาที | ตาม intent | ผู้เชี่ยวชาญด้านน้ำท่วม หรือเจ้าของผลิตภัณฑ์ |
| 2 | ช่วงความลึก และเกณฑ์ระดับความรุนแรง | 1 ถึง 300 ซม. และเกณฑ์ชั่วคราว 15 / 30 | ผู้เชี่ยวชาญด้านน้ำท่วม |
| 3 | อายุแฮช IP และข้อกำหนด PDPA | 24 ชั่วโมง ยังไม่มีประกาศความเป็นส่วนตัว | ฝ่ายกฎหมาย |
| 4 | ข้อความป้ายเตือนที่เพียงพอทางกฎหมาย | ตามตาราง 1.2 | ฝ่ายกฎหมาย |

| 6 | รายการคำนำหน้าที่ตัดตอนจับคู่จุดสังเกต | ตามตาราง 1.2 | เจ้าของผลิตภัณฑ์ (ปรับหลังเห็นข้อมูลจริง) |
